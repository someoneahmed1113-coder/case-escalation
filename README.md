# منصة تصعيد الحالات | تجمع الحدود الشمالية الصحي

منصة لتوثيق ومتابعة الحالات التي تواجه تحديات وتحتاج إلى الدعم والتوجيه، مبنية على «نموذج تصعيد الحالات» لإدارة التنسيق الطبي بالتجمع.

## سير العمل

1. **التنسيق الطبي** يدخل بالبريد وكلمة المرور، وينشئ الطلب (بيانات الحالة، مركز 1937، المستشفى المعني) ويوقّع.
2. يرسل التنسيق **رابطاً خاصاً بالطلب** إلى المستشفى عبر الواتساب.
3. **الطبيب المعالج** يفتح الرابط بدون كلمة مرور، ويكتب الرأي الطبي والإجراء المتخذ واسمه ويوقّع. يظهر الرد فوراً عند التنسيق.
4. يتابع التنسيق، ويرسل عند الحاجة لـ**قائد المسار للتخصص** أو **إدارة المستشفيات** أو أي جهة أخرى، وكل جهة تكتب إفادتها وتوقّع.
5. يحدّث التنسيق نتيجة التصعيد، ويصدّر النموذج كاملاً بصيغة PDF موثقاً بكل التواقيع.

## الصلاحيات

| | التنسيق الطبي | الطبيب / المستشفى / الجهات |
|---|---|---|
| الدخول | بريد وكلمة مرور | رابط خاص بدون كلمة مرور |
| بيانات الحالة | إنشاء وتعديل | قراءة فقط |
| خانة الجهة | قراءة فقط | تعبئة مرة واحدة ثم تُقفل |
| ردود الجهات الأخرى | قراءة | قراءة فقط |
| الحذف | غير متاح لأحد، للحفاظ على التوثيق | غير متاح |

* الحماية مطبّقة داخل قاعدة البيانات نفسها (Row Level Security ودوال محددة)، وليست في الواجهة فقط.
* كل رابط يحمل رمزاً عشوائياً طوله 48 حرفاً، ويمكن للتنسيق إلغاؤه قبل استخدامه.
* بعد توقيع أي جهة لا يمكن تعديل ردها حتى من قاعدة البيانات عبر الواجهة.
* كل حدث (إنشاء، إرسال، فتح الرابط، توقيع، تغيير الحالة، ملاحظة) يُسجّل تلقائياً في سجل المتابعة.

## مكونات المشروع

```
index.html        الدخول ولوحة الطلبات السابقة
request.html      إنشاء الطلب ومتابعته وإرساله
respond.html      صفحة الطبيب والجهات (بدون كلمة مرور)
config.js         عنوان قاعدة البيانات ومفتاحها العام (الملف الوحيد الذي يتغير عند النقل)
assets/           الهوية: الشعار، النقش، خط Janna LT، التنسيق والسكربتات
supabase/migrations/001_init.sql   الجداول والصلاحيات والدوال
```

لا يحتاج المشروع أي بناء أو تثبيت: ملفات ثابتة تعمل على أي استضافة (GitHub Pages أو سيرفر المنشأة).

## التشغيل لأول مرة

1. أنشئ مشروعاً جديداً في Supabase، ثم نفّذ `supabase/migrations/001_init.sql` من SQL Editor.
2. من **Authentication → Providers → Email** عطّل خيار **Allow new users to sign up**، حتى لا يسجل أحد بنفسه.
3. أضف كل منسق من **Authentication → Users → Add user** (بريد وكلمة مرور)، ثم سجّله في فريق التنسيق:
   ```sql
   insert into public.staff (user_id, full_name, phone)
   select id, 'اسم المنسق', '05xxxxxxxx' from auth.users where email = 'coordinator@example.com';
   ```
   لإيقاف منسق: `update public.staff set active = false where user_id = '...';`
4. ضع عنوان المشروع والمفتاح العام (anon key) في `config.js`.
5. انشر الملفات (مثلاً GitHub Pages من الفرع `main`).

بدون تعبئة `config.js` تعمل المنصة في **وضع العرض التجريبي** الذي يحفظ البيانات في المتصفح فقط، وهو مخصص للمعاينة.

## النقل إلى سيرفر المنشأة

المنصة لا تعتمد على أي خدمة خاصة بالسحابة:

1. ثبّت Supabase المستضاف ذاتياً (Docker) على سيرفر المنشأة، أو أي PostgreSQL مع PostgREST وGoTrue.
2. نفّذ ملف `001_init.sql` نفسه، وانقل البيانات بـ `pg_dump` من المشروع الحالي عند الحاجة.
3. انسخ الملفات الثابتة إلى خادم الويب، وعدّل `config.js` بعنوان السيرفر الجديد ومفتاحه.

المشاريع الأخرى في حساب Supabase لا تتأثر، لأن لكل مشروع قاعدة بيانات مستقلة.

## ملاحظات

* تصدير PDF يتم عبر نافذة الطباعة في المتصفح (اختر «حفظ بتنسيق PDF»)، ويخرج بنمط النموذج الورقي على ورقة A4.
* التوقيع يُحفظ صورةً داخل قاعدة البيانات مع اسم الموقّع ووقت التوقيع.
* لا تُدخل بيانات شخصية للمريض؛ رقم الإحالة يكفي وفق سياسة الخصوصية المعتمدة.
